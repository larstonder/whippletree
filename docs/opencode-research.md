## Detail notes by research question

### 1. Plugin contract
- Signature: `export type Plugin = (input: PluginInput, options?: PluginOptions) => Promise<Hooks>` — async factory confirmed.
- `PluginInput`: `client` (opencode SDK client bound to the running server), `project`, `directory` (cwd), `worktree` (git worktree root), `experimental_workspace.register(type, adapter)`, `serverUrl` (getter, `URL`), `$` (Bun shell, possibly `undefined`). No `env` map is passed in directly — plugins that need env read `process.env` themselves, and can *set* outgoing shell env via the separate `shell.env` hook.
- Directories: `.opencode/plugin/` or `.opencode/plugins/` (project), same two names under the global config dir (`~/.config/opencode/` by default, XDG/`OPENCODE_CONFIG_DIR`-overridable). Extensions `.ts`/`.js` only for these directory-scanned files.
- npm plugin package names: yes, bare string or `[name, options]` tuple in `config.plugin` array; installed via `bun install`-equivalent into `~/.cache/opencode/node_modules/` per docs (not independently source-verified in this pass — flag as docs-only for that specific cache path claim, though `install.ts`/`loader.ts` source confirms the general resolve→install→import pipeline).
- Types package: `@opencode-ai/plugin`, subpath exports also include `./tool`, `./tui`, `./v2/promise`, `./v2/effect*` — a v2 API (Promise- and Effect-based) already exists in the same package for what looks like a forthcoming plugin API generation, worth a follow-up look if the opencode-2.0 rename lands mid-project.
- Runtime: Bun-first (`$` only populated under Bun); no evidence of a hard per-plugin sandbox — a plugin is just an imported module with full ambient access.

### 2. Event/hook surface
See table rows 12-14 above for the full list and throw semantics. Key structural point for the Whippletree plan: **there is no per-hook-return "block/allow" contract like Claude Code's hook JSON decisions.** Blocking is achieved only by throwing (soft, tool-call-scoped) or by the internal `Permission.Service` deny path (which the `permission.ask` hook can only nudge via `output.status`, not fully author — the internal ruleset evaluation in `packages/opencode/src/permission/index.ts` runs regardless of the plugin hook and can independently deny/ask/allow).

### 3. Tool identity
Confirmed IDs (as they'll appear in `tool.execute.before/after` `input.tool` and `tool.definition` `input.toolID`): `bash`, `read`, `write`, `edit`, `apply_patch`, `glob`, `grep`, `webfetch`, `websearch` (id `"websearch"`, defined at `packages/opencode/src/tool/websearch.ts` line ~100 as `Tool.define("websearch", ...)` — correcting an earlier assumption of `"search"`, which was actually the *registry map key*, not the tool `id`), `skill`, `lsp`, `plan_exit` (not `plan` — `PlanExitTool` is `Tool.define("plan_exit", ...)`), `task` (from `const id = "task"` in `task.ts`), plus `todo`/`question`/`invalid` (ids not explicitly grepped this pass, follow registry key names `todo`/`question`/`invalid` by convention — treat those three specifically as UNVERIFIED-exact-string, everything else in this paragraph is grep-confirmed against `Tool.define("<id>", ...)` call sites).

### 4. Subprocess spawning
`ctx.$` is `Bun.$` when the host process is Bun (the normal case — opencode ships/runs as a Bun program). Plugins can also just `import { spawn } from "child_process"` or any node/bun API directly since they're regular modules; no sandbox layer was found restricting this. `directory`/`worktree` in `PluginInput` give a project-root anchor for cwd; there's no separate `env` object handed to the plugin factory (read `process.env` directly, or intercept outgoing shell env via the `shell.env` hook, which explicitly hands you `{ cwd, sessionID?, callID? }` in and lets you mutate `output.env`).

### 5. Install + headless e2e
- macOS install: brew tap `anomalyco/tap/opencode`, `npm install -g opencode-ai`, or curl installer (docs-verified, not independently confirmed against a Homebrew formula file in this pass).
- Headless: `opencode run "prompt"` (docs-verified); `opencode serve` + `--attach` for warm-server iteration, useful for a class-1 e2e harness that wants to inspect plugin-hook side effects across multiple runs without cold-start cost each time.
- Config: project `opencode.json`/`opencode.jsonc` (walked up to nearest git root, per `ConfigPaths.files`), global `~/.config/opencode/opencode.json`, XDG-overridable (source-verified, contra docs prose).
- Pre-auth plugin/hook firing: UNVERIFIED by direct run this pass (see row 20) — structurally plausible from the Effect dependency graph (`Plugin.node` doesn't depend on `Provider`/`Auth`), but flagged as the plan's first thing to empirically test, exactly as requested.
- Isolation via env: `XDG_CONFIG_HOME`, `XDG_DATA_HOME`, `XDG_CACHE_HOME`, `XDG_STATE_HOME` all honored through the `xdg-basedir` npm package (source-verified); `OPENCODE_CONFIG_DIR` flag as a direct override; DB path also independently overridable via `OPENCODE_DB` flag/env.

### 6. Version/velocity
`opencode-ai@latest` = 1.18.10 (published during this research session), `@opencode-ai/plugin@latest` = 1.18.9. ~20 releases in the trailing 30 days, frequently 2+ same-day releases. The `dev` npm dist-tag (`0.0.0-dev-202607301413`) and a `2.0` git branch both exist — active pre-release churn alongside the stable channel. The one concrete forward-looking break already visible in source: the `bash` tool-id/permission-key rename is explicitly deferred to "opencode 2.0" (comment in `shell/id.ts`), meaning a Whippletree tool-name mapping table keyed on `"bash"` today will need a compat shim whenever 2.0 ships — no timeline found for that cut.

### 7. Session storage
SQLite (via `drizzle-orm/sqlite-core`, per-platform driver split `sqlite.bun.ts`/`sqlite.node.ts`), single file `opencode.db` (or `opencode-<channel>.db`) under `Global.Path.data` (`$XDG_DATA_HOME/opencode/`, override via `OPENCODE_DB`). This replaces whatever "JSON per message" scheme the prior matrix-level pass assumed — a T4 observer should target SQLite reads (schema churns often; `packages/core/src/database/schema.gen.ts` and the migration folder are the ground truth for current table shape at any given commit, not a fixed schema to hardcode against).
